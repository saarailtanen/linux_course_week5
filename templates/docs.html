Request path

Browser → Nginx (port 80) → Unix socket → Gunicorn + Flask → Ollama / MariaDB

The browser sends every request to Nginx on port 80. The /viikko5/ location removes the prefix and passes the request over the Unix socket /run/chatapp/gunicorn.sock to Gunicorn, which runs the Flask app. Flask reads and writes the conversation in MariaDB (127.0.0.1:3306, database chatapp) and sends the messages to Ollama (127.0.0.1:11434), which runs the language model locally on the same server. The reply is streamed back token by token. Ollama listens only on localhost and the app only on the socket, so the only public ports of the server are 80 (HTTP) and 22 (SSH).

Pipeline (GitHub Actions)

  • Pull requests and every push: the job Lint and tests runs ruff (lint), pytest and a syntax check of the shell scripts. The tests replace Ollama and MariaDB with fakes, so they need neither the model nor the production database.
  • Push to main: the same checks run first. Only if they pass, the job Deploy to cPouta runs (it has needs: test). It copies the code with rsync to /opt/chatapp/app, runs deploy.sh on the server, and then makes a public smoke test.
  • What deploy.sh does: installs the Python dependencies into a virtual environment, writes the commit SHA of the run into a REVISION file, applies the database schema, installs the Nginx snippet (nginx -t first; the old snippet is restored if the test fails), and restarts only the chatapp service. Other services are not touched.
  • How a deployment is verified: deploy.sh asks Gunicorn through the socket which commit it is running. The workflow then requires /viikko5/health to return exactly the commit SHA of the run (github.sha). The value comes from the deployment, it is not written by hand. A mismatch fails the workflow.
  • A failing test is not deployed: if the test job is red, the deploy job is skipped. Failed run: PASTE_FAILED_RUN_URL

/opt/chatapp/appOwner ubuntu. rsync sets directories to 755 and files to 644, so the service can read the code but not change it.
/etc/chatapp/chatapp.env-rw-r----- 1 root chatapp: owner root, group chatapp, mode 640. It holds the database password and the settings, so only root and the service user can read it. It is not in the repository.
/run/chatapp/gunicorn.socksrwxrwx--- 1 chatapp chatapp: the Unix socket is owned by chatapp and has mode 770. Nginx runs as www-data, which is a member of the group chatapp, so it can use the socket.
MariaDB user chatapp@localhostOwn database chatapp. Privileges: only SELECT, INSERT on chatapp.* (the schema is applied by root during the deployment). The password is random and stored only in the env file.

SSH access for GitHub Actions

GitHub runners connect from changing IP addresses, so a rule that allows only my own IP would block them. Port 22 was already open to 0.0.0.0/0 in the cPouta security group from the earlier weeks, so I did not need to change the security group. The server accepts only key login: sshd -T reports passwordauthentication no and pubkeyauthentication yes. The security implications of this choice: sshd is reachable from the whole internet, so only the keys protect it; the deploy key logs in as ubuntu, which has sudo, so a leaked key would give full control of the server. The private key exists only as a GitHub secret and in my own .ssh folder, outside the repository, and it can be revoked by deleting its line from authorized_keys on the server.

How /viikko5/ was added to Nginx

The repository contains only a snippet with location blocks and no server block. I added one line, include snippets/chatapp.conf;, inside the server block of the existing site (/etc/nginx/sites-enabled/default), after making a backup copy of the file. deploy.sh keeps the snippet file itself up to date and never edits the site file. The ^~ modifier on the locations keeps the site's regex locations from catching /viikko5/ requests. Gunicorn uses a Unix socket, so it cannot clash with the Week 2 app, which already uses port 8000. The Week 2 page at the root of the server still answers after the change and after every deployment.

Model and server resources

Model: qwen2.5:0.5b, 397 MB (shown by ollama list). The server (server A, a cPouta virtual machine) has only 937 MiB of RAM, so a larger model would not fit. It has no GPU: the Ollama installer printed the warning "No NVIDIA/AMD GPU detected. Ollama will run in CPU-only mode", so replies are slower, especially the first one after a start, when the model is loaded into memory. Because there was no swap, I added a 2 GB swap file (/swapfile, created with fallocate, mkswap and swapon, and an entry in /etc/fstab so it survives a reboot). I develop the application and run the local checks (ruff and pytest) on my Windows laptop; the model runs only on server A.

Week 4 and replication

The chat is installed on server A, because the MariaDB on server B is a read-only replica and could not store messages. The chat database is not replicated to B: A's binlog_do_db lists only counterdb, so changes to chatapp are not written to the binary log, and B's replicate_do_db also lists only counterdb. The chat history therefore exists only on A. Replicating it would only be useful if B had to show the chat read-only, which it does not.

One problem I solved

My first deployment failed after only 4 seconds, although the job Lint and tests was green. The log of the rsync step said /home/runner/.ssh/config line 3: no argument after keyword "user" and rsync exited with code 255. That showed that the problem was not in the code but in how the workflow connects: it builds the SSH configuration from the GitHub secrets, and the CPOUTA_USER secret had no usable value, so the User line was empty. I saved the secret again with the value ubuntu (GitHub never shows a secret value again, so saving it again is the only way to check it) and re-ran the failed job without a new commit. The deployment then went green and /viikko5/health returned the commit SHA. I learned to read the log of the exact failing step, and that a deployment that fails within seconds points to the connection setup or the secrets rather than to the application.
