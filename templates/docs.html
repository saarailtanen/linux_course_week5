Request path

Browser → Nginx (port 80) → Unix socket → Gunicorn + Flask → Ollama / MariaDB

The browser sends every request to Nginx on port 80. The /viikko5/ location removes the prefix and passes the request over the Unix socket /run/chatapp/gunicorn.sock to Gunicorn, which runs the Flask app. Flask reads and writes the conversation in MariaDB (127.0.0.1:3306, database chatapp) and sends the messages to Ollama (127.0.0.1:11434), streaming the model reply back token by token. Ollama and the app listen only on localhost or on the socket; the only public ports are 80 and 22.

Pipeline

  • Pull requests and every push: ruff lint, pytest (Ollama and MariaDB are mocked, so no model or production database is needed) and a syntax check of the shell scripts.
  • Push to main: the same checks; only if they pass, a second job deploys. rsync copies the code to /opt/chatapp/app, deploy.sh installs the dependencies, applies the database schema, installs the Nginx snippet (nginx -t first, the old snippet is restored if it fails), restarts only the chatapp service and checks the version.
  • Verification: deploy.sh asks Gunicorn through the socket which commit it is running, and the workflow then requires /viikko5/health to return the commit SHA of the run (github.sha). A mismatch fails the workflow.
  • Failing tests: the deploy job has needs: test, so a red test job means no deployment. Failed run: PASTE_FAILED_RUN_URL

SSH access for GitHub Actions

GitHub runners connect from changing IP addresses, so port 22 is open to 0.0.0.0/0 in the cPouta security group (this rule was already in place from the earlier weeks, so I did not need to change the security group). Password login is disabled (sshd -T reports passwordauthentication no and pubkeyauthentication yes), so only key login works. The risks: sshd is reachable from the whole internet, and the deploy key gives a shell as ubuntu with sudo, so it must never leak. The private key exists only as a GitHub secret and in my own .ssh folder, and it can be revoked by deleting its line from authorized_keys.

How /viikko5/ was added to Nginx

The repository contains only a snippet with location blocks and no server block. I added one line, include snippets/chatapp.conf;, inside the server block of the existing site, and deploy.sh keeps the snippet itself up to date; the deployment never edits the site file. The ^~ modifier keeps the site's regex locations from catching /viikko5/ requests. Gunicorn uses a Unix socket, so it cannot clash with the Week 2 app that already uses port 8000. I checked the earlier pages after every deployment and they stayed at their URLs.

Model and server resources

Model: qwen2.5:0.5b (about 400 MB; the exact size is in the ollama list output below). Swap: the server has only 937 MiB of RAM and had no swap, so I added a 2 GB swap file (/swapfile, created with fallocate, mkswap and swapon, and an entry in /etc/fstab so it survives a reboot). The server is a cloud virtual machine without a GPU: Ollama printed the warning No NVIDIA/AMD GPU detected and runs in CPU-only mode, so replies are slower and I chose a small model. I develop and run the local checks (ruff and pytest) on my Windows laptop, but the model runs only on server A.

Week 4 and replication

The chat is installed on server A, because the MariaDB on server B is a read-only replica and could not store messages. The chat database is not replicated to B: A's binlog_do_db lists only counterdb, so changes to chatapp are not written to the binary log, and B's replicate_do_db also lists only counterdb. The chat history therefore exists only on A. Replicating it would only be useful if B had to show the chat read-only, which it does not.

One problem I solved

My first deployment failed after only 4 seconds, although the Lint and tests job was green. The log of the rsync step said /home/runner/.ssh/config line 3: no argument after keyword "user" and rsync exited with code 255. That showed the problem was not in the code but in how the workflow connects: it builds the SSH configuration from the GitHub secrets, and the CPOUTA_USER secret was empty, so the User line had no value. I re-entered the secret with the value ubuntu (GitHub never shows secret values again, so re-entering is the only way to check one) and re-ran the failed job without a new commit. The deployment went green and /viikko5/health returned the commit SHA. I learned to read the log of the exact failing step, and that a deploy that fails within seconds points at connection setup or secrets rather than at the application.
